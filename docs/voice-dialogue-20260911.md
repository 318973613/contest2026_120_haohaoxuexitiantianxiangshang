## 现场结论

用户确认已烧录上一轮镜像、语音识别较准确，但报告唤醒后没有正常回答、界面唤醒词与识别词不一致、提醒没有同步到主页倒计时，以及唤醒后未自动进入语音页。

现场日志的 `25 chunks, 80000 read, 0 sent` 是约 2.5 秒的批量 ASR 录音窗口，不是早期只采到一块 PCM 的故障。`0 sent` 指没有流式发送；后面明确调用了 batch ASR，并有成功识别文本。仅凭这段循环，不能断言已经向聊天模型连续发送了问题，也不能只归因于模型思考慢。

本次接续了另一任务未完成的候选代码，没有覆盖原有 TLS 任务组隔离、录音所有权、触摸队列、G2D、FreeType、popen 栈和 nxplayer stdin 修复。

## 烧录后验收

1. 先在本地更新有效 MiMo 凭据，不把 Key 发到聊天。核对新镜像与配对 ELF 后，按本人确认的流程烧录；若直接烧录本次原始镜像，仍需更新其旧 Key。冷启动检查开机音频、串口、WiFi 和基本触摸。
2. 停留主页，说“你好小米”。应自动进入语音页；单独唤醒应有本地短提示音，然后显示正在听。
3. 说“给我一条学习建议”，检查识别、等待、回答和播报。连续再问两次，等待/播报期间不能出现新问题重复提交，触摸和返回应保持可用。
4. 再测试一句“你好小米，三十秒后提醒我休息”。AI 确认工具成功后返回主页，应出现提醒圆环；到期提醒后恢复专注显示。原专注统计不应被改写。
5. 设置一分钟提醒后，在主页点圆环旁的取消按钮；取消完成后不应到时再播报。慢回复期间返回页面，迟到的本轮语音回复不应突然播放。

关键串口标记：`wake phrase matched`、`question submitted: wake-...; recording paused`、`still waiting; no new recording`。后一条表示继续等待同一个请求，不表示又发了一条消息。提供日志前隐藏密钥、Authorization 和 WiFi 密码。

## 边界与借鉴

- 唤醒仍然使用联网批量 ASR，后台识别耗时和云端调用开销仍存在；不是离线唤醒，不保证固定秒数回复。
- 简单静音端点在很轻、很短的语音或噪声环境下可能等到 10 秒上限，须用板端麦克风实测后调整，不能仅凭主机数据调阈值。
- 退出页面不强杀正在执行的云端请求；它会抑制迟到播报，直到请求完成前保留必要的音频/请求协调。
- 主页只展示最近一个本地提醒，不是所有提醒列表；专注计时仍独立运行。
- 已参考 [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32) 的分阶段语音反馈和音频协调思路；没有直接移植 ESP-IDF/ESP-SR，也不把 ESP32 离线唤醒能力宣称为 R528 已实现。
- 公共 `packages/ai_agent` 改动保留在公共仓本地，后续需对应 fork/PR。专属仓只接收自身 UI 与文档，不混入公共仓源码。未提交、未推送。
